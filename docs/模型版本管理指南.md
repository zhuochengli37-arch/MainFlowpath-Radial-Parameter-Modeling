# 模型版本管理指南

## 1. 文档目的

本文说明项目如何保存模型元数据，以及预测阶段如何做版本兼容性检查。

## 2. 为什么要做版本管理

模型文件能否加载，并不代表结果一定可信。  
如果训练环境和预测环境差异过大，可能出现：

- 模型无法加载；
- 能加载但结果不可比；
- 依赖版本差异导致预测行为变化。

因此项目在保存模型的同时，也会保存对应元数据。

## 3. 当前涉及的主要流程

当前版本管理主要覆盖这些正式工作流：

- `python -m project1 current benchmark-1d`
- `python -m project1 current benchmark-2d`
- `python workbase/current_scripts/workline_pipeline.py`
- `python -m project1 current benchmark-3d`
- `python -m project1 current predict-1d`
- `python -m project1 current predict-3d`

兼容脚本入口仍然存在，但当前正式说明以统一入口为主。

## 4. 会保存哪些内容

训练输出通常包括：

- 模型文件，例如 `.pkl`；
- 同名或关联的元数据文件，例如 `.json`；
- 排行榜；
- benchmark 报告；
- 配置快照。

## 5. 元数据通常包含的信息

模型元数据通常会记录：

- 模型名称；
- 训练时间；
- 输入列与输出列；
- 训练数据路径；
- 关键配置；
- 依赖版本信息；
- 评估指标。

## 6. 预测阶段会检查什么

预测时的版本检查通常会关注：

1. 模型文件是否存在；
2. 元数据文件是否存在；
3. 关键依赖是否兼容到足以加载模型；
4. 当前输入结构是否与训练结构匹配。

## 7. 当前工作流差异

### 7.1 `predict-1d`

会对模型元数据做较明确的兼容性检查。

### 7.2 `predict-3d`

会对模型元数据做较明确的兼容性检查，并结合分区与目标量选择最佳模型。

### 7.3 `predict-2d`

当前以可加载性检查为主，还没有完全达到 1D / 3D 同等粒度的版本检查深度。

## 8. 配置快照与版本管理的关系

每次训练成功后，程序会把当时生效的配置复制到输出目录中，常见文件包括：

- `run_config_latest.yaml`
- `run_configs/benchmark_config_YYYYMMDD_HHMMSS.yaml`

这对复现实验非常重要，因为它能补足“模型文件之外的训练上下文”。

## 9. 常见输出位置

例如：

- `data/current/3d/DATACASE1/output/models/`
- `data/current/1d/sample6/output/models/`
- `data/generic/1d/output/`
- `data/generic/2d/output/`

## 10. 推荐实践

建议按以下原则管理模型：

1. 模型文件和元数据文件始终一起保留；
2. 配置快照不要删除；
3. 尽量不要混用来自无关环境训练出的模型；
4. 如果依赖版本漂移较大，优先考虑重新训练；
5. 对正式交付结果，保留排行榜和报告文件。

## 11. 常见问题

### 11.1 为什么会提示“模型版本不兼容”

因为程序发现当前环境与模型训练环境差异较大，为避免误用，会发出警告或直接失败。

### 11.2 找不到元数据文件怎么办

如果元数据丢失，模型有时仍可能加载，但版本校验能力会下降。正式使用时不建议忽略这一点。

### 11.3 为什么配置快照也要一起留存

因为模型效果不仅取决于算法，还取决于：

- 输入路径；
- 分区方式；
- 折数；
- 是否启用 GPR；
- 预测筛选指标。
